# PokeChess 개인 학습 계획 — 2026-07-21

## 공부할 주제

### 분산 상태 동기화와 멱등한 재접속 설계

PokeChess를 개발하면서 Photon API 사용법보다 더 깊게 이해해야 한다고 느낀 부분은 **여러 클라이언트에 나뉜 게임 상태를 연결 손실과 권한 이전 이후에도 일관되게 복구하는 방법**입니다.

현재 보드 상태는 각 플레이어가 소유하고 팀 HP와 공용 상점 풀은 MasterClient가 관리합니다. 이 구조에서는 재접속, 후입장, MasterClient 교체, RPC 중복·유실이 겹쳐도 최종 상태가 같아야 합니다. 따라서 분산 상태의 소유권과 복구 원칙을 집중적으로 공부합니다.

## 학습 목표

1. authoritative state, eventual consistency, idempotency의 차이를 설명할 수 있다.
2. Photon의 Room Properties, Player Properties, RPC의 전달·캐시·순서 특성을 비교할 수 있다.
3. 상태별 소유자, 최종 진실원, 복구 출처를 명확하게 정의할 수 있다.
4. snapshot revision으로 오래된 메시지와 중복 메시지를 거부하는 규칙을 설계할 수 있다.
5. 재접속, 후입장, MasterClient 교체 상황을 반복 가능한 테스트로 재현할 수 있다.
6. 현재 PUN2 구조를 전용 서버 구조로 바꿀 경우 클라이언트와 서버의 책임이 어떻게 달라지는지 설명할 수 있다.

## 학습 순서

### 1단계: 개념 정리

- 권한 서버와 클라이언트 권한 모델 비교
- 강한 일관성과 최종 일관성 비교
- 멱등성, 중복 제거, 메시지 순서 보장 학습
- 스냅샷과 이벤트 로그 방식 비교

### 2단계: 현재 프로젝트 분석

- 보드, 라운드, 팀 HP, 공용 상점 풀의 상태 소유자 정리
- 각 상태가 Room Properties, Player Properties, RPC, 로컬 필드 중 어디에 저장되는지 정리
- 연결 손실 후 어떤 데이터로 상태를 복구하는지 추적
- MasterClient 교체 시 새 MasterClient가 전달받지 못하는 상태가 있는지 확인

### 3단계: 코드와 테스트 개선

- 같은 스냅샷을 두 번 받아도 결과가 달라지지 않는 테스트 작성
- 낮은 revision의 스냅샷을 무시하는 테스트 작성
- 재접속 직전과 직후의 revision, round, phase를 구조화 로그로 기록
- 연결 손실 중 MasterClient만 라운드를 진행한 뒤 두 클라이언트가 같은 상태로 수렴하는지 검증
- MasterClient 교체와 재접속이 연속으로 발생하는 시나리오 검증

## 직접 만들어 볼 결과물

- 상태별 소유자·저장 위치·복구 출처 표
- 재접속 및 MasterClient 교체 시퀀스 다이어그램
- 네트워크 상태 전이 체크리스트
- 2클라이언트 회귀 테스트 시나리오
- 실패 상황별 로그 예시와 판정 기준

## 학습 완료 기준

- 현재 네트워크 구조를 다른 사람에게 그림으로 설명할 수 있다.
- 각 공유 상태의 최종 진실원이 무엇인지 즉시 답할 수 있다.
- 중복·지연·유실 메시지가 들어와도 상태가 망가지지 않는 이유를 코드와 테스트로 증명할 수 있다.
- 재접속 또는 MasterClient 교체 버그가 발생했을 때 로그만 보고 어느 단계에서 불일치가 생겼는지 추적할 수 있다.
- 현재 PUN2 구조의 한계와 전용 서버로 전환해야 하는 조건을 설명할 수 있다.
