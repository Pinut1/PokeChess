# PokeChess 3차 멘토링 질문지

## 프로젝트 한 줄 소개

Unity URP와 Photon PUN2로 개발 중인 **2인 협동 PvE 포켓몬 TFT 스타일 오토배틀 게임**입니다. 두 플레이어가 각자 보드와 상점을 운영하고, 같은 라운드의 보스·적을 공략해 팀 단위 결과를 냅니다.

개발자는 2명이며 담당은 다음과 같습니다.

- Core / Network / 전투 / 보드
- 상점 / 아이템 / UI

## 현재 구현 상태

- 2인 매칭, 동시 씬 전환, 준비 및 라운드 동기화
- 각자 보드 권위 + 파트너 보드 읽기 전용 미러
- MasterClient 권위의 공용 챔피언 풀과 팀 공용 HP
- Stage 데이터 기반 PvE 적 생성과 자동 전투
- 상점, XP, 아이템, 진화, 증강, 전적 저장
- 연결 끊김 감지와 60초 재접속 유예
- 유닛·골드 전송 백엔드

현재 가장 큰 고민은 **재접속 상태 복구, 보스 기믹 구조, 데이터 기반 스킬 확장, 네트워크 검증 및 프로젝트 마무리 우선순위**입니다.

## 우선 질문

### 1. 현재 네트워크 권위 구조가 협동 오토배틀에 적절한가요?

현재는 각 플레이어가 자기 보드·골드의 권위자이고, 공용 챔피언 풀과 팀 HP만 MasterClient가 관리합니다. 전투도 각 클라이언트가 자신의 PvE 전투를 로컬에서 시뮬레이션하고 승패 결과만 모읍니다.

질문:

- 2인 협동 PvE 프로토타입에서 이 정도 분산 권위 구조가 적절한가요?
- 실서비스를 고려한다면 서버 또는 MasterClient 권위로 옮겨야 할 상태는 무엇인가요?
- 치팅보다 동기화 안정성이 중요한 소규모 프로젝트라면 어디까지 검증하는 것이 현실적인가요?

### 2. 재접속 상태 복구는 어떤 단위로 설계하는 것이 좋은가요?

현재 `ReconnectAndRejoin`, PlayerTtl, 재접속 유예와 씬 재로드 방지는 구현되어 있습니다. 하지만 보드 스냅샷은 비버퍼 RPC라 재접속 중 변경된 보드·벤치·라운드 상태를 완전히 복구하지 못합니다.

질문:

- Room/Player CustomProperties에 지속 상태를 모두 저장하는 방식과, 재접속 시 현재 권위자에게 전체 스냅샷을 요청하는 방식 중 어느 쪽을 추천하시나요?
- 보드, 벤치, 상점 예약, 라운드, 준비 상태에 각각 revision을 두는 것이 과한 설계일까요?
- 재접속 복구에서 반드시 대비해야 하는 순서 역전·중복 처리·MasterClient 교체 사례가 궁금합니다.

### 3. 보스 전용 기믹을 확장 가능하게 만들려면 어떤 구조가 좋을까요?

현재 보스는 Stage 데이터상 타입과 스탯 배수로만 구분되고, 일반 적과 동일한 전투 루프를 사용합니다. 앞으로 HP 구간별 페이즈, 소환, 광역 공격, 전조, 협동 대응 패턴을 추가하려고 합니다.

질문:

- 보스별 MonoBehaviour를 만드는 방식, 상태 머신, Strategy 패턴, 데이터 기반 행동 트리 중 현재 규모에 가장 적합한 접근은 무엇인가요?
- 일반 스킬 시스템과 보스 전용 기믹의 경계를 어디에 두는 것이 유지보수에 좋을까요?
- 첫 보스 세로 슬라이스를 구현할 때 꼭 넣어야 할 디버깅/관측 기능은 무엇인가요?

### 4. 스킬·증강 효과를 어디까지 데이터화하는 것이 좋을까요?

일반 스킬은 `effectType`, 대상, 범위, 수치 등을 데이터로 관리하지만, 특수 영웅증강은 코드에서 임시 스킬 데이터를 생성하거나 전용 분기를 사용하고 있습니다. 예를 들어 나인이볼부스트는 8종 소환과 종별 버프처럼 일반 스킬 모델로 표현하기 어려운 효과입니다.

질문:

- 모든 효과를 범용 effectType으로 만들기보다 특수 효과는 전용 코드로 두는 것이 나을까요?
- 데이터 정의와 전용 실행 코드가 함께 필요한 경우 어떤 인터페이스나 레지스트리 구조를 추천하시나요?
- 범용화가 지나쳐 개발 속도가 느려지는 시점을 판단하는 기준이 있을까요?

### 5. GameEvents 중심의 매니저 통신 구조를 계속 유지해도 될까요?

현재 팀 규칙상 매니저끼리 직접 참조하지 않고 정적 `GameEvents`를 통해 통신합니다. 초기에는 결합도를 낮추기 좋았지만, 이벤트 수가 늘면서 발행자·구독자 추적과 실행 순서 파악이 어려워지고 있습니다.

질문:

- 소규모 Unity 프로젝트에서 정적 이벤트 버스를 사용할 때 흔히 발생하는 문제는 무엇인가요?
- 조회는 명시적 인터페이스, 상태 변경은 이벤트로 분리하는 방식이 더 나을까요?
- 이벤트 누수, 중복 구독, 실행 순서 문제를 실무에서는 어떻게 검증하거나 시각화하나요?

### 6. 유닛·골드 전송의 피어 ACK 구조가 안전한가요?

현재 보내는 쪽이 자원을 선차감하거나 pending 상태로 잡고, 상대가 벤치 공간·수신 가능 여부를 확인한 뒤 ACK를 보내면 송신 측에서 최종 제거합니다. 실패하면 유지 또는 환급합니다.

질문:

- 연결이 ACK 직전 끊기거나 RPC가 중복 도착하는 경우 복사·소실을 막으려면 transaction ID와 멱등 처리가 필수일까요?
- MasterClient 검증을 추가하는 것과 현재 피어 간 트랜잭션을 유지하는 것 중 어느 쪽이 더 적절한가요?
- 이런 거래성 네트워크 기능에서 실무적으로 사용하는 상태 전이와 타임아웃 처리 방법이 궁금합니다.

### 7. Photon 2클라이언트 기능은 어떻게 자동 검증하는 것이 좋을까요?

현재 ParrelSync와 수동 2클라이언트 테스트에 의존합니다. 공유 풀, 재접속, 마스터 교체, 유닛·골드 전송은 타이밍에 따라 버그가 발생할 가능성이 큽니다.

질문:

- Unity/PUN2 환경에서 네트워크 통합 테스트를 어느 수준까지 자동화할 수 있을까요?
- 네트워크 계층을 추상화해 로컬 fake transport로 상태 전이를 테스트하는 방식이 실효성이 있나요?
- 기능 프리즈 전에 반드시 수행해야 할 네트워크 시나리오와 로그 항목을 추천해주실 수 있나요?

### 8. 현재 남은 작업 중 포트폴리오와 재미 검증 관점에서 무엇을 우선해야 할까요?

남은 큰 작업은 재접속 완전 복구, 파트너 보드 모델 표시, 통신기 정식 UI, 나인이볼부스트, 보스 기믹, 특수 스킬 데이터화입니다. 개발 인원과 기간이 제한되어 모두 높은 완성도로 구현하기는 어렵습니다.

질문:

- 현업 면접 또는 포트폴리오에서 더 높게 평가될 가능성이 있는 것은 네트워크 안정성, 확장 가능한 전투 구조, 실제 플레이 재미 중 무엇인가요?
- 현재 상태라면 반드시 완성할 2~3개와 과감히 제외할 항목을 어떻게 고르시겠나요?
- “기술적으로 많이 구현했지만 게임이 덜 다듬어진 상태”를 피하려면 어떤 마감 기준을 세워야 할까요?

## 시간이 남으면 드릴 질문

### 9. MasterClient 권위의 공용 챔피언 풀

공유 풀은 MasterClient가 구매 예약·확정·반환을 처리하고 revision 스냅샷을 배포합니다. MasterClient 교체 시 기존 mirror에서 권위를 이어받습니다. 이 방식에서 놓치기 쉬운 경쟁 조건이나 데이터 유실 사례가 있을까요?

### 10. 파트너 보드 미러의 구현 범위

현재 speciesId·성급·위치는 동기화하지만 캡슐로만 표시합니다. 실제 모델을 표시할 때 `PokemonUnit` 전체를 생성하지 않고 순수 View 전용 객체를 따로 두는 것이 좋을까요?

### 11. 구글 시트 → JSON → ScriptableObject 파이프라인

구글 시트를 원본으로 두고 JSON 변환과 Unity Importer를 거쳐 SO를 읽기 전용 캐시로 사용합니다. 이 구조에서 스키마 버전 관리, 데이터 검증, CI 검사를 어떤 방식으로 보강하는 것이 좋을까요?

### 12. 2인 개발팀의 코드 소유권

담당 영역을 나누었지만 UI와 Network처럼 경계를 넘는 기능에서 대기 시간이 생깁니다. 소규모 팀에서 코드 소유권을 유지하면서 병목을 줄이는 리뷰·인터페이스 합의 방식이 궁금합니다.

### 13. 프로파일링과 최적화 시점

현재 전투 유닛과 파트너 미러 일부는 primitive 생성·전체 재생성 방식을 사용합니다. 작은 보드 규모에서도 초기에 풀링과 프로파일링 기준을 잡는 것이 좋을지, 실제 병목이 확인된 뒤 최적화하는 것이 좋을지 궁금합니다.

3. 보스 페이즈·소환·협동 패턴을 확장하려면 어떤 런타임 구조가 가장 현실적인가요?
4. 특수 스킬은 범용 데이터 모델과 전용 코드 중 어디까지 나누는 것이 좋을까요?
5. 제한된 기간에 포트폴리오와 재미 검증을 위해 반드시 완성할 작업은 무엇인가요?
