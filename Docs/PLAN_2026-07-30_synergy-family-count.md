# 시너지 카운트 규칙 정정 — 진화 계열 기준으로 변경

작성 2026-07-30 · 기획 확정: 황해인 · 구현 담당: 시너지/보드 파트

---

## 1. 현상

같은 진화 계열의 여러 진화 단계를 필드에 동시에 올리면 시너지가 **각 단계마다 따로** 카운트된다.

```
이상해씨(1성) + 이상해풀(2성) + 이상해꽃(3성)  →  현재: 풀3 독3   기대: 풀1 독1
```

원인은 [`SynergyManager.RecalculateSynergies()`](../Assets/_Project/Scripts/Managers/SynergyManager.cs)가 카운트 키로 **도감 번호(`unit.data.id`)** 를 쓰기 때문이다.

```csharp
species.Add(unit.data.id); // 같은 종 중복은 HashSet이 걸러줌
```

같은 *종* 중복은 걸러지지만, 3합체 진화 시 `unit.data`가 진화체로 통째로 스왑되므로(`BoardManager`) 이상해씨(1)·이상해풀(2)·이상해꽃(3)이 서로 다른 id가 되어 3카운트가 된다.

**영향 범위: 41개 진화 계열.** 최대 ×3까지 부풀려진다.

| 계열 | 부풀림 |
|---|---|
| 이상해씨 > 이상해풀 > 이상해꽃 | 풀 ×3, 독 ×3 |
| 파이리 > 리자드 > 리자몽 | 불꽃 ×3 |
| 구구 > 피죤 > 피죤투 | 노말 ×3, 비행 ×3 |
| 뿔충이 > 딱충이 > 독침붕 | 벌레 ×3, 독 ×3 |

불꽃·비행·노말·정령·대지·전기·벌레·파괴·드래곤의 1티어가 `2`이므로, **한 계열만 세워도 즉시 발동**한다. 조합 다양성을 보상한다는 시너지의 전제가 무너져 있다.

## 2. 기획 의도

시너지는 **"서로 다른 종류를 모았다"에 대한 보상**이다. 판단 기준은 *상점에서 몇 번의 독립된 투자를 했는가*이지, 필드 위 기물이 몇 개인가가 아니다.

- 이상해씨를 사서 3합체로 이상해꽃을 만든 것은 **하나의 투자**다. 그 과정의 중간 산물을 같이 세워둔다고 종류가 늘어난 게 아니다.
- 반대로 **버프는 필드에 올라간 개체 전원이 받아야 한다.** 카운트에 기여하지 않는다고 해서 이상해씨가 풀 버프를 못 받으면 플레이어 입장에서 납득이 안 된다. (카운트 = 조건, 버프 = 결과. 둘의 단위가 다르다.)

**핵심 원칙**

> 카운트는 **계열 단위**, 버프는 **개체 단위**.

## 3. 확정 규칙

### 3-1. 카운트 단위 — 진화 계열 루트 기준

카운트 키를 `(시너지, 종id)`에서 **`(시너지, 진화계열 루트id)`** 로 바꾼다.
진화 루트는 세 갈래를 **모두** 하나의 계열로 본다.

| 진화 루트 | 데이터 소스 | 계열 병합 |
|---|---|---|
| 3합체(성급) 진화 | `PokemonData.evolvesIntoEn` | O |
| 진화의 돌 | `EvolutionStoneDatabase` | O |
| 통신교환 진화 | `TradeEvolutionData` | O |

시너지마다 별도 집합으로 세므로, **겹치는 시너지는 1회 / 겹치지 않는 시너지는 각자** 카운트되는 동작이 자동으로 나온다.

### 3-2. 버프 적용 — 현행 유지

[`BattleManager.ApplySynergyBuffs()`](../Assets/_Project/Scripts/Managers/BattleManager.cs)는 "해당 트레잇을 보유한 아군 전원"에게 버프를 건다. **수정하지 않는다.** 카운트가 1이어도 이상해씨·이상해풀·이상해꽃 셋 다 풀 버프를 받는다.

### 3-3. 예외 — 돌연변이(Mutant)

이브이 계열 9종은 **각자 1카운트씩 세야 한다.** 진화체를 모으는 것 자체가 돌연변이 시너지의 설계이므로, 계열로 묶으면 시너지가 성립하지 않는다.

`SynergyData`에 `countPerSpecies` 플래그를 신설해 **데이터로** 예외를 표현한다. 돌연변이만 `true`, 나머지는 `false`(기본값).

### 3-4. 돌연변이 봇 — 현행 유지

돌연변이 시너지로 소환되는 봇(에브이·브래키·글레이시아·님피아)은:

- **레벨별 유닛 캡에 포함되지 않는다**
- **시너지를 카운트하지 않는다**

- **시너지 스탯버프를 받지 않는다**
- 단, 치어리더 선택 버프와 얼음 적군 디버프는 **팀 기준 적용을 유지**한다 (봇도 대상)

현재 구현이 이미 이 스펙대로다. 봇은 `source = null`로 생성되어 BattleManager의 전투 목록에만 들어가고 BoardManager의 보드에는 등록되지 않으며, SynergyManager는 보드를 pull하므로 봇이 잡히지 않는다. 소환 시점도 전투 시작이라 카운트 확정 이후다. **코드 수정 없음 — 회귀 방지를 위해 명문화만 한다.**

> 참고: 봇 4종의 시너지는 전부 `["Mutant"]` 하나뿐이고 돌연변이는 스탯버프가 없는 특수 시너지(봇 소환)다. 따라서 `source == null` 가드와 무관하게 봇이 받을 스탯버프는 애초에 존재하지 않는다. 향후 봇에 다른 시너지를 부여하는 기획이 생기면 이 항목을 재검토한다.

## 4. 케이스별 기대 결과

실제 데이터로 계열 루트를 계산해 검증한 결과다.

| 필드 구성 | 계열 루트 | 현재 | 기대 |
|---|---|---|---|
| 이상해씨 + 이상해풀 + 이상해꽃 | 전부 `이상해씨` | 풀3 독3 | **풀1 독1** |
| 스라크[벌레·비행] + 핫삼[벌레·파괴] | 둘 다 `스라크` | 벌레2 비행1 파괴1 | **벌레1 비행1 파괴1** |
| 별가사리[물] + 아쿠스타[물·정령] | 둘 다 `별가사리` | 물2 정령1 | **물1 정령1** |
| 피카츄 + 라이츄 | 둘 다 `피츄` | 전기2 | **전기1** |
| 이브이 + 샤미드 + 부스터 | (예외) | 돌연변이3 | **돌연변이3** (유지) |
| 돌연변이 봇 4마리 | — | 카운트 없음 | **카운트 없음** (유지) |

> **스라크/핫삼 케이스 보충** — 통신진화는 진화 즉시 종이 바뀌므로 한 필드에 전후 단계가 공존할 수 없다. 유일한 예외가 협동 플레이에서 파트너가 대신 진화시켜 진화체를 되돌려주는 경우다. 정상적인 플레이 흐름은 아니지만, 발생 시 카운트가 어긋나지 않도록 규칙에 포함한다.

## 5. 구현 구조

### ① `EvolutionFamily` 정적 유틸 신설 — `Assets/_Project/Scripts/Data/EvolutionFamily.cs`

진화 루트가 코드에 세 갈래로 흩어져 있으므로, 계열 정의를 프로젝트에 **하나만** 두기 위한 유틸.

```csharp
public static class EvolutionFamily
{
    /// <summary>이 종이 속한 진화 계열의 최초 종 id. 계열 루트면 자기 자신.</summary>
    public static int RootId(PokemonData data);

    /// <summary>DB 리임포트/도메인 리로드 시 캐시 무효화.</summary>
    public static void Invalidate();
}
```

**빌드 방식** — `PokemonDatabase` 전체를 훑어 `자식 → 부모` 맵을 만든 뒤 루트까지 거슬러 올라간다(결과는 캐시).

1. `PokemonData.evolvesIntoEn` → `evolvesIntoEn`을 자식, 자기 자신을 부모로 등록
2. `EvolutionStoneDatabase`의 `evolvedPokemon → targetPokemon`
3. `TradeEvolutionData`의 `evolvedPokemonEn → targetPokemonEn` (이미 `_reverseLookup`이 있으므로 재사용)

주의사항:

- **부모가 이미 등록된 종은 덮어쓰지 않는다**(최초 등록 우선). 한 종이 여러 루트의 결과가 되는 경우를 대비.
- **사이클 가드 필수** — 방문 집합 또는 최대 깊이로 무한 루프를 막는다. 데이터가 잘못 들어와도 게임이 멈추면 안 된다.
- 매니저가 아닌 static 유틸이므로 프로젝트 규칙(매니저끼리 직접 참조 금지)에 걸리지 않는다.

### ② `SynergyManager` 카운트 키 교체

```csharp
// 변경 전
species.Add(unit.data.id);

// 변경 후
species.Add(synergyData.countPerSpecies
    ? unit.data.id                          // 돌연변이: 종별 카운트
    : EvolutionFamily.RootId(unit.data));   // 그 외: 계열별 카운트
```

`SynergyStatus.uniqueCount`의 의미가 "보드 위 고유 종 수"에서 **"고유 계열 수"** 로 바뀌므로 주석을 갱신한다. UI(`SynergyHud`, `SynergyPanelUI`)는 `uniqueCount` 값만 읽으므로 **수정 불필요**.

### ③ `SynergyData.countPerSpecies` 플래그 신설

- 구글 시트에 `countPerSpecies` 컬럼 추가 → `synergy_data.json` → `SynergyData` (기본값 `false`)
- `PokeChessImporter`의 시너지 임포트에 필드 매핑 추가
- **돌연변이 행만 `true`**
- 적용하려면 `PokeChess/Import Synergy JSON` 재실행 필요

기본값이 `false`라 기존 행은 영향받지 않는다. 나중에 같은 성격의 시너지가 추가돼도 코드 수정 없이 데이터로 처리된다.

### ④ (선택) `ShopManager` 진화 맵 통합 — **별도 티켓 권장**

[`ShopManager.BuildEvolutionToBaseMap()`](../Assets/_Project/Scripts/Managers/ShopManager.cs)이 이미 3합체 사슬을 절반쯤 같은 방식으로 구현해두었다. 다만 **용도가 다르다.**

| | SynergyManager | ShopManager |
|---|---|---|
| 필요한 것 | 계열의 **최초 종** | 상점 풀에 **되돌릴 기본종** |
| 루트 범위 | 전체 DB | 구매 가능 종만 |

예를 들어 라이츄를 팔았을 때 `EvolutionFamily` 기준 루트는 피츄지만, 상점 풀에 되돌려야 하는 건 실제 풀 소속 종이다. **이 차이를 무시하고 통합하면 상점 풀이 오염된다.** 이번 수정 범위에서 제외하고, 통합 시에는 판매 → 풀 반환 회귀 테스트를 반드시 동반한다.

### 파괴 T3에 대한 기획 의도

파괴 4계열 중 둘은 **통신교환으로만** 파괴 트레잇을 얻는다.

| 계열 | 파괴 보유 종 | 획득 경로 |
|---|---|---|
| 코일 | 코일 · 레어코일 · 자포코일 | 상점 |
| 리오르 | 리오르 · 루카리오 | 상점 |
| 롱스톤 | **강철톤만** | 통신교환 |
| 스라크 | **핫삼만** | 통신교환 |

즉 파괴 최고 티어는 파트너와의 통신교환 2건 성공이 전제다. **2인 협동 PVE라는 게임 컨셉상 의도된 설계**이며, 솔로 진행으로는 T2까지가 상한이다. 수치를 낮추지 않는다.

### 티어 개수가 바뀌는 시너지 — 수치 테이블 동반 수정

시너지 *수치*는 JSON이 아니라 `SynergyConstants`의 코드 상수다. 드래곤은 티어가 3개 → 2개로 줄므로 배열도 함께 줄인다.

```csharp
// 변경 전
["DRAGON"] = new[] { 0.15f, 0.30f, 0.50f },
// 변경 후
["DRAGON"] = new[] { 0.20f, 0.40f },
```

**의도** — 드래곤 6종은 전부 고코스트(미뇽 계열 cost4, 딥상어동 계열 cost3)이고 계열이 2개뿐이다. 티어가 1/2로 줄면 T1은 "고코스트 1종 확보", T2는 "드래곤 2계열 전부 확보"로 **요구 난이도가 오히려 올라간다.** 따라서 진입 수치를 15% → 20%로 올려 고코스트 1종 투자에 값하게 하고, 최종은 40%로 잡아 2계열 완성의 보상을 남기되 기존 50%보다는 낮춰 과열을 막는다.

풀은 티어 개수가 4개 그대로라 `["GRASS"]` 배열은 수정 불필요하다.

## 7. 검증 체크리스트

- [ ] 이상해씨 + 이상해풀 + 이상해꽃 → 풀1 독1, 셋 다 풀·독 버프 수혜
- [ ] 피카츄 + 라이츄 → 전기1, 둘 다 전기 버프 수혜
- [ ] 별가사리 + 아쿠스타 → 물1 정령1
- [ ] 이브이 + 샤미드 + 부스터 → 돌연변이3 (예외 정상 동작)
- [ ] 돌연변이 봇 소환 후 시너지 카운트 불변, 유닛 캡 불변
- [ ] 진화 직후 카운트 즉시 갱신 (진화는 보드 변경 이벤트를 타므로 재계산 트리거 확인)
- [ ] 계열 중 하나를 판매했을 때 카운트가 정상 감소
- [ ] 협동 상대에게서 통신교환으로 받은 진화체가 내 보드에서 올바른 계열로 병합
- [ ] 시너지 패널 표기와 실제 발동 티어 일치

> 자동 테스트는 런타임 코드가 predefined assembly에 있어 붙지 않는다(프로젝트 CLAUDE.md 참고). `Scripts/Debug/` 하네스로 카운트를 덤프해 확인한다.

## 8. 작업 순서

1. `EvolutionFamily` 유틸 신설 + 사이클 가드
2. `SynergyData.countPerSpecies` 필드 + 임포터 매핑 + 시트/JSON 갱신(돌연변이만 `true`) → 임포트 재실행
3. `SynergyManager` 카운트 키 교체 + 주석 갱신
4. 시트에 티어 수치 반영(풀 `2/4/6/8`, 드래곤 `1/2`) → `synergy_data.json` → 임포트 재실행
5. `SynergyConstants`의 `DRAGON` 배열을 2개로 축소
6. 검증 체크리스트 수행

1~3은 서로 독립적이라 병렬 진행 가능하다. **모든 티어 수치는 기획 확정 완료 — 대기 항목 없음.**
