# 통신 진화 재설계 조사 — 2026-07-22

> 상태: 구현 전 데이터·코드 대조 완료. 기획 결정이 필요한 항목은 이 문서 하단에 분리했다.
> 기준: `master` / Unity 6000.3.8f1 / Unity MCP로 실제 `Resources` SO 로드 결과 확인.

## 확정 결정

### 1. 발동 성급 제한 없음 — 성급을 유지한 종 교체 (2026-07-22)

통신 진화는 플레이어에게는 진화로 보이지만 런타임 규칙상 **성급 상승이 아니라 캐릭터(종) 교체**다.

```text
1성 스라크 -> 1성 핫삼
2성 스라크 -> 2성 핫삼
3성 스라크 -> 3성 핫삼
```

- 1성도 통신 진화 대상이며 최소 성급이나 정확히 2성 같은 제한은 없다.
- 변환 전 `starLevel`을 그대로 보존한다.
- 변환 후 같은 진화체 3마리를 모으면 기존 합체 규칙으로 다음 성급이 된다.
- 상점에서 원본 대신 제공되는 진화체도 1성으로 생성되고, 1성 3마리 -> 2성, 2성 3마리 -> 3성으로 합체한다.
- 공용 풀 회계는 원본 카피를 기준으로 유지한다. 따라서 1/2/3성 진화체는 각각 원본 카피 1/3/9개를 대표한다.
- 통신 진화체 플래그와 `x1.5` 특수진화 배율은 합체 뒤에도 유지해야 한다.

현재 `BoardManager.CheckEvolution()`은 생존 유닛의 `data`와 `starLevel`을 갱신하지만 `isTradeEvolved`를 초기화하지 않으므로, 통신 진화체끼리 합체하는 경우 생존자 플래그는 유지된다. 다만 상점 override로 새로 생성되는 진화체에도 반드시 `isTradeEvolved=true`와 원본 풀 ID를 설정해야 한다.

### 2. 실시간 단방향 전송 — 상호 교환 불필요 (2026-07-22)

통신기는 TFT 더블업의 대포처럼 파트너에게 기물을 보내는 장치다. TFT처럼 별도의 교환 라운드를 두지 않고 게임 진행 중 계속 사용할 수 있다.

```text
플레이어 A가 유닛을 통신기에 넣음
  -> 파트너 B가 해당 유닛을 받음
  -> A의 유닛은 성공 ACK 뒤 제거
```

- A와 B가 동시에 유닛을 맞교환할 필요가 없다.
- 한 플레이어가 주기만 하거나 받기만 해도 된다.
- 전송 1건은 독립적인 단방향 트랜잭션이다.
- 기존 `SendTradeUnit -> RPC_TradeReceive -> RPC_TradeAck`의 원자적 전송 골격은 재사용할 수 있다.
- 상대 벤치가 가득 찼거나 수신 생성에 실패하면 거부하고 송신자 유닛을 유지한다.
- 통신 진화 대상이면 전송된 유닛의 성급을 유지한 채 수신 측에서 진화체로 생성한다.

### 3. 수신 플레이어에게 영구 광역변환 적용 (2026-07-22)

통신 진화 대상 유닛을 받은 플레이어에게 해당 원본 종의 영구 override가 활성화된다.

```text
A가 스라크를 전송
  -> B가 같은 성급의 핫삼을 받음
  -> B가 현재 보유한 스라크도 핫삼으로 변환
  -> 이후 B의 상점에는 스라크 대신 핫삼 등장
```

- 광역변환의 소유자는 송신자 A가 아니라 **수신자 B**다.
- A의 필드·벤치·상점에는 영향을 주지 않는다.
- B의 현재 원본 유닛은 위치와 성급을 유지한 채 진화체로 종만 교체한다.
- B의 이후 상점 롤은 공용 풀의 원본 스라크 카피를 예약하지만 B에게는 핫삼으로 표시·생성한다.
- 한 번 활성화된 원본->진화체 override는 해당 매치 동안 유지하는 영구 상태로 구현하는 것이 현재 설명과 일치한다.
- **확정: 보드뿐 아니라 벤치의 동일 원본도 수신 즉시 전부 진화체로 바꾼다.**
- **확정: 현재 열린 상점 슬롯의 동일 원본도 수신 즉시 진화체로 바꾼다.** 다음 리롤부터만 적용하는 방식이 아니다.
- 잠긴 상점에 원본 2장이 떠 있고 골드 부족으로 다음 라운드 구매를 계획한 상황에서도, 통신 진화를 받으면 그 두 슬롯이 즉시 진화체로 바뀌어야 한다.
- 현재 상점의 잠금 여부, 슬롯 위치, 공용 풀 예약 ID와 revision은 그대로 유지하고 표시 데이터와 구매 생성 결과만 진화체로 투영한다.
- **확정: 한 번 활성화된 원본->진화체 override는 해당 매치가 끝날 때까지 영구 유지한다.**
- **확정: 재접속 후에도 활성화 상태를 복구한다.** Local Player CustomProperties에 활성 매핑을 저장하고, 재입장 시 보드·상점 상태를 적용하기 전에 복원해야 한다.
- **확정: 구매 가격과 판매 환급은 원본 종 기준으로 유지한다.** 진화체 데이터의 표시 코스트가 달라지더라도 통신 진화 경제 계산에는 원본 `poolOriginPokemonId`의 코스트를 사용한다.
- **확정: 공용 풀 반환도 원본 종 기준이다.** 1/2/3성 진화체 판매 시 원본 카피 1/3/9개를 반환한다.
- **확정: 통신 진화로 종이 교체돼도 장착물은 새 캐릭터가 그대로 승계한다.** 일반 아이템과 진화의 돌을 제거하거나 인벤토리로 반환하지 않는다.
- 진화의 돌로 이미 다른 종이 된 유닛도 원본 계보가 통신 진화 대상이면 함께 통신 진화체로 교체한다. 예: 물의돌 야도란도 야도킹으로 바뀌고 물의돌은 장착 슬롯에 남는다.
- **확정: 영구 통신 진화 뒤 진화의 돌을 제거해도 통신 진화체 종을 유지한다.** 돌만 인벤토리로 돌아가며 원본이나 돌 진화체로 되돌아가지 않는다.

## 결론

현재 구현은 폐기된 모델A에 고정돼 있다.

- 내 벤치 유닛 1마리를 파트너에게 보낸다.
- 받는 쪽이 매핑을 조회해 자기 벤치에 진화체 1마리를 생성한다.
- 성공 ACK 뒤 보낸 쪽 유닛을 제거한다.

최신 방향인 **즉시·비가역 진화 + 실행 플레이어의 필드·벤치·상점 광역변환**을 구현하려면 단순히 `SendTradeUnit`의 대상을 바꾸는 수준으로는 부족하다. 특히 공용 상점 풀은 예약된 원본 ID를 구매 ACK 검증에 사용하므로, 상점 슬롯을 진화체 ID로 직접 덮어쓰면 구매가 실패한다.

권장 구조는 다음과 같다.

1. 공용 풀의 재고·예약·구매 프로토콜은 계속 **원본 포켓몬 ID**를 사용한다.
2. 플레이어별 통신 진화 상태를 별도로 보관한다.
3. 해당 플레이어의 상점에서만 원본 슬롯을 진화체로 표시한다.
4. 구매 승인·풀 반환은 원본 ID로 처리하고, 실제 생성되는 유닛만 진화체 데이터로 해석한다.
5. 기존 필드·벤치 유닛은 위치와 성급을 유지한 채 `PokemonData`를 교체하고 영구 통신진화 플래그를 설정한다.

## 확인한 현재 데이터 경로

```text
Assets/Resources/Data/trade_evolution_data.json
  -> PokeChessImporter.ImportTradeEvolutions()
  -> Assets/Resources/TradeEvolution_Data.asset
  -> TradeEvolutionData.Instance
  -> NetworkManager.RPC_TradeReceive()
```

JSON과 생성된 SO의 매핑 9개는 일치한다. 현재 스키마는 아래 세 필드뿐이다.

```csharp
targetPokemonEn
evolvedPokemonEn
note
```

최신 기획에 있는 다음 필드는 아직 JSON, SO, 임포터 어디에도 없다.

```text
affectsField
affectsBench
affectsShop
isReversible
```

현재 9개 매핑:

| 원본 | 진화체 | 원본 상점 획득 | 진화체 상점 획득 |
|---|---|---:|---:|
| Golbat | Crobat | 불가 | 불가 |
| Kadabra | Alakazam | 불가 | 불가 |
| Abra | Kadabra | 가능 | 불가 |
| Graveler | Golem | 불가 | 불가 |
| Geodude | Graveler | 가능 | 불가 |
| Slowpoke | Slowking | 가능 | 불가 |
| Haunter | Gengar | 불가 | 불가 |
| Onix | Steelix | 가능 | 불가 |
| Scyther | Scizor | 가능 | 불가 |

`Golbat`, `Kadabra`, `Graveler`, `Haunter`는 `shopBuyable=false`다. 어떤 경로로 원본을 얻는지와 통신 진화 발동 성급이 확정되지 않으면 일부 매핑은 실제 플레이에서 도달하지 못할 수 있다.

또한 현재 데이터에는 검토가 필요한 관계가 있다.

- **`Golbat -> Crobat`은 확정된 게임 고유 규칙이다.** 원작의 친밀도 진화를 별도 시스템으로 구현하기 어려워 통신 진화로 대체한다.
- **`Kadabra -> Alakazam`이 정식 통신 진화다.** `Abra -> Kadabra`는 잘못 추가된 중간 진화 행이므로 제거한다. 후딘(`Alakazam`, id 65)은 현재 PokemonDatabase에 존재한다.
- **`Graveler -> Golem`이 정식 통신 진화다.** `Geodude -> Graveler`는 잘못 추가된 중간 진화 행이므로 제거한다. 딱구리(`Golem`, id 76)는 현재 PokemonDatabase에 존재한다.
- `Slowpoke.evolvesIntoEn = Slowbro`인데 `Slowking.evolvesIntoEn = Wobbuffet`로 들어가 있다.
- JSON의 `note`도 Abra와 Geodude 행을 일반 진화 가능성이 있는 추정치로 표시하고 있어 제거 결정과 일치한다.

따라서 Golbat 행은 유지하고, 나머지 미확정 행은 기획 원본과 한 번 더 대조해야 한다. 이 프로젝트에서는 원작 진화 방식보다 게임 구현을 위해 확정한 대체 규칙을 우선한다.

## 스탯 기준 검증

`PokemonData`의 런타임 계약은 명확하다.

- SO의 `hp`, `attack`, `spellPower`는 원본값이다.
- 별 배율은 데이터에 저장하지 않고 `PokemonUnit.StarMultiplier`에서 일괄 적용한다.
- 1성 `1.0`, 2성 `1.8`, 3성 `3.24`다.
- 통신 진화체는 여기에 `SPECIAL_EVOLUTION_MULTIPLIER = 1.5`가 추가된다.

현재 계산식:

```text
유효 스탯 = PokemonData 값 x 성급 배율 x 통신진화 1.5
```

따라서 2성 통신 진화체는 SO 값의 `2.7배`다. 예:

| 진화체 | SO HP/ATK/SP | 현재 2성 통신진화 결과 |
|---|---|---|
| Steelix | 1300 / 60 / 80 | 3510 / 162 / 216 |
| Scizor | 700 / 50 / 65 | 1890 / 135 / 175.5 |
| Slowking | 900 / 35 / 180 | 2430 / 94.5 / 486 |

임포터는 JSON 값을 그대로 SO에 기록하며 성급 기준을 나타내는 필드가 없다. 그러므로 **현재 코드 계약만 보면 모든 진화체 데이터도 1성 기준**이다.

외부 Pokemon DB 가이드가 진화체 값을 정말 2성 완성값으로 직접 입력하도록 규정한다면 현재 계약과 충돌한다. 그 경우 런타임에서 추측해 보정하지 말고 다음 중 하나로 데이터 계약을 확정해야 한다.

- 권장: 모든 포켓몬 시트 스탯을 1성 기준으로 통일한다.
- 대안: 명시적 `statBasisStar`를 추가하고 임포터에서 1성 기준으로 정규화한다.

`SPECIAL_EVOLUTION_MULTIPLIER = 1.5` 자체는 설계 의도이므로 제거 대상이 아니다.

## 코드 충돌 지점

### 1. 공용 풀 ID와 상점 표시 ID가 결합돼 있음

공용 풀은 다음 흐름으로 동작한다.

```text
MasterClient가 원본 pokemonId로 슬롯 예약
  -> 해당 ID로 클라이언트 상점 스냅샷 생성
  -> 구매 요청은 revision + slot
  -> MasterClient가 예약에서 원본 pokemonId 반환
  -> 클라이언트가 _slots[slot].id == pokemonId 검증 후 생성
```

통신 진화 뒤 `_slots[slot]`을 진화체로 직접 바꾸면 마지막 ID 검증이 실패한다. 해결하려면 슬롯에 아래 두 개념을 분리해야 한다.

```text
poolSource: 공용 풀 예약·반환에 사용하는 원본 PokemonData/ID
offered: 플레이어에게 표시하고 실제 생성할 PokemonData
```

기존 UI 호환을 위해 `CurrentSlots`는 `offered`를 계속 반환할 수 있다. 내부에는 원본 ID 배열 또는 `ShopSlotState`를 별도로 둔다.

### 2. 기존 예약 슬롯도 즉시 변환돼야 함

`affectsShop=true`가 “이후 상점”뿐 아니라 현재 열려 있는 상점에도 적용되는지 명시가 필요하다. 현재 문구의 “상점에도 원본 대신 진화체만 등장”을 엄격히 적용하면 활성화 시 기존 예약 슬롯의 표시도 즉시 바뀌어야 한다.

이때도 MasterClient 예약 ID는 원본으로 유지하고 로컬 표시만 진화체로 투영해야 한다.

### 3. 판매 시 원본 풀 반환 경로가 없음

`ShopManager._evolvedToBase`는 `PokemonData.evolvesIntoEn` 일반 진화 사슬만 역매핑한다. 통신 진화 매핑은 이 사슬에 포함되지 않으므로, 통신 진화체를 팔아도 원본 카피가 풀에 복귀하지 않을 수 있다.

전역 종 역매핑보다 유닛별 원산지 기록이 안전하다.

```csharp
PokemonUnit.poolOriginPokemonId
```

- 상점 구매 시 예약된 원본 ID를 기록한다.
- 일반 합체 후에도 생존자에 유지한다.
- 통신 진화로 데이터가 교체돼도 유지한다.
- 판매 시 `poolOriginPokemonId`와 성급 카피 수(1/3/9)를 공용 풀에 반환한다.

이 방식은 같은 진화체에 여러 획득 경로가 생겨도 모호하지 않다.

### 4. `OnUnitChanged`에 구독자가 없음

`PokemonUnit.TryEquipStone()`과 `RemoveStone()`은 데이터 교체 뒤 `GameEvents.UnitChanged()`를 발행하지만 현재 `OnUnitChanged` 구독자는 0명이다.

통신 진화에서 데이터만 바꾸면 다음 갱신이 자동으로 보장되지 않는다.

- 보드 시너지 재계산
- 파트너 보드 스냅샷 재전송
- UI 카드/툴팁 갱신
- 3D 모델 교체

통신 진화 구현 전에 `OnUnitChanged`의 소비자를 명확히 연결하거나, 위치에 따라 기존 `UnitPlaced`/`UnitBenched` 이벤트를 다시 발행해야 한다. 다만 후자는 의미상 “이동”이 아닌데 이동 이벤트를 재사용하는 문제가 있어 `OnUnitChanged`를 정상 연결하는 쪽을 권장한다.

### 5. 데이터 스왑만으로 3D 모델이 교체되지 않음

`UnitFactory`는 생성 시점에만 `data.modelPrefab`을 인스턴스화한다. 이후 `PokemonUnit.data`를 바꾸는 일반 진화·진화의 돌 경로에는 모델을 다시 만드는 코드가 없다.

통신 진화 광역변환은 `PokemonUnit`의 비주얼 교체 API 또는 별도 UnitView 갱신 경로가 필요하다. 기존 자식 모델과 콜라이더를 안전하게 교체하고, 보드/벤치 위치와 드래그 루트는 유지해야 한다.

## 권장 런타임 설계

### 활성화 상태

플레이어마다 원본 ID에서 진화체 ID로 가는 영구 매핑을 유지한다.

```text
localTradeEvolutionOverrides[targetId] = evolvedId
```

멀티플레이 재접속을 고려하면 이 상태는 로컬 메모리에만 두지 말고 Local Player CustomProperties에도 직렬화한다. 파트너에게 보이는 보드 스냅샷은 이미 최종 speciesId를 보내므로 별도 렌더링 규칙은 필요 없다.

### 이벤트 흐름

매니저 직접 참조 금지 규칙을 유지한다.

```text
통신기 트리거
  -> GameEvents.TradeEvolutionRequested(unit)
  -> BoardManager가 대상/성급/상태를 검증하고 활성화 확정
  -> GameEvents.TradeEvolutionActivated(mapping)
     -> BoardManager: 필드·벤치의 동일 원본 변환
     -> ShopManager: 플레이어별 상점 override 등록 + 현재 슬롯 표시 갱신
     -> NetworkManager: Player CustomProperties 저장
     -> UIManager: 결과/실패 사유 표시
```

활성화 성공과 실패 이벤트를 분리하고, 여러 매니저가 요청 이벤트에 제각각 반응해 부분 적용되는 구조는 피한다.

### 보드·벤치 변환

`BoardManager`가 `GetUnitsOnBoard()`와 `GetUnitsInBench()` 결과를 스냅샷으로 만든 뒤 대상 종만 변환한다.

각 유닛은 다음을 유지한다.

- 현재 보드 좌표 또는 벤치 슬롯
- 성급
- 장착 아이템
- 현재 HP는 새 MaxHP 이하로 clamp
- 풀 원산지 ID

각 유닛은 다음을 변경한다.

- `data = evolvedData`
- `isTradeEvolved = true`
- 모델/아이콘/시너지/역할/스킬 갱신

진화의 돌이 장착된 유닛과 `evolutionLocked` 유닛의 우선순위는 기획 결정 전까지 임의 처리하지 않는다.

### 상점 변환

공유·로컬 상점 모두 같은 슬롯 모델을 사용한다.

```text
ShopSlotState
  poolSourcePokemonId
  offeredPokemonData
```

- 롤과 예약 차감: `poolSourcePokemonId`
- 골드 비용: 원본 비용을 권장하나 기획 확정 필요
- UI 표시: `offeredPokemonData`
- 구매 생성: `offeredPokemonData`
- 판매 풀 반환: 유닛의 `poolOriginPokemonId`
- 리롤 미구매 반환: `poolSourcePokemonId`

MasterClient의 `_remainingPool`과 `_sharedReservations`는 원본 ID만 유지하므로 플레이어별 변환 상태 때문에 공용 재고가 갈라지지 않는다.
