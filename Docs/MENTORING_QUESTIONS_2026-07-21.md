# PokeChess 현업 멘토링 질문지 — 2026-07-21

## 인사와 프로젝트 소개

안녕하세요. 저희는 Unity로 2인 협동 PVE 오토배틀 게임 **PokeChess**를 개발하고 있습니다.

두 플레이어가 각자의 보드와 상점을 운영하면서 같은 스테이지와 보스를 공략하는 구조이며, 네트워크는 Photon PUN2를 사용합니다. 현재 전투, 보드, 상점, 진화, 증강, 전적 기록 같은 핵심 기능은 대부분 구현했고, 재접속 안정화와 실제 콘텐츠 연결, 정식 UI, 밸런스 작업을 진행하고 있습니다.

저는 Core, Network, 전투, 보드 영역을 담당하고 있습니다. 개발하면서 기술적으로 판단이 어려웠던 부분을 중심으로 질문드리고 싶습니다.

## 우선 질문

### 1. 네트워크 상태의 소유권을 지금처럼 나눠도 괜찮을까요?

현재 각 플레이어는 자기 보드 상태를 소유하고, 팀 HP와 공용 상점 풀처럼 두 플레이어가 공유하는 상태는 MasterClient가 관리합니다. 재접속이나 MasterClient 교체가 발생하면 revision이 포함된 스냅샷을 다시 전송합니다.

이 구조가 2인 협동 게임에 적절한지, 실무 관점에서 위험한 부분이 있는지 의견을 듣고 싶습니다.

추가로 여쭤볼 내용:

- MasterClient에 맡겨도 되는 상태와 별도 서버 권한이 필요한 상태를 어떤 기준으로 구분하나요?
- Room Properties, Player Properties, RPC 중 무엇을 최종 상태의 기준으로 두는 것이 안전한가요?
- 재접속과 MasterClient 교체가 연속으로 발생해도 같은 결과가 나오게 하려면 어떤 상태를 반드시 저장해야 하나요?

### 2. 멀티플레이 재접속 테스트는 어느 수준까지 자동화해야 할까요?

현재 EditMode 테스트 외에도 Unity Editor 두 개와 ParrelSync를 이용해 연결 손실, 재접속, 라운드 복구를 직접 검증하고 있습니다. 하지만 실제 클라이언트 두 개를 사용하는 테스트는 실행 시간이 길고 자동화하기 어렵습니다.

실무에서는 멀티플레이 테스트를 단위 테스트, PlayMode 테스트, 실제 다중 클라이언트 테스트로 어떻게 나누는지 궁금합니다.

추가로 여쭤볼 내용:

- 반드시 자동화해야 하는 네트워크 시나리오는 무엇인가요?
- 자동화하기 어려운 테스트는 어떤 로그와 체크리스트를 남겨야 재현성을 확보할 수 있나요?
- 프로토타입에서 서비스 가능한 수준으로 넘어갈 때 사용하는 품질 기준이 있나요?

### 3. 정적 이벤트 버스를 계속 사용해도 괜찮을까요?

현재 매니저끼리 직접 참조하지 않고 정적 `GameEvents`를 통해 통신하도록 규칙을 정했습니다. 결합도는 낮아졌지만, 이벤트가 많아질수록 누가 발행하고 구독하는지 추적하기 어려워질 수 있다고 느끼고 있습니다.

프로젝트가 커졌을 때도 이 구조를 유지해도 되는지, 인터페이스 주입이나 다른 구조로 나눠야 하는 시점이 언제인지 조언을 듣고 싶습니다.

추가로 여쭤볼 내용:

- 이벤트 버스가 오히려 의존성을 숨기기 시작했다는 신호는 무엇인가요?
- 이벤트 순서, 중복 발행, 구독 해제 누락은 실무에서 어떻게 방지하나요?
- 모든 통신을 이벤트로 처리하지 않는다면 어떤 기능을 직접 인터페이스로 분리하는 것이 좋을까요?

### 4. 현재 데이터 파이프라인을 언제까지 유지해도 될까요?

기획 데이터는 구글 시트를 원본으로 두고, JSON으로 내보낸 뒤 Unity 임포터가 ScriptableObject에 베이킹합니다. ScriptableObject는 읽기 전용 캐시로 취급하고 런타임에서는 베이킹된 데이터를 사용합니다.

이 방식이 프로토타입과 소규모 출시 단계까지 적절한지, JSON 직로드나 Addressables 같은 구조로 전환해야 하는 기준이 궁금합니다.

추가로 여쭤볼 내용:

- 문자열 ID와 테이블 간 참조는 임포트 단계에서 어디까지 검증해야 하나요?
- 잘못된 데이터가 있을 때 경고 후 계속 진행하는 것과 임포트를 중단하는 기준은 무엇인가요?
- 구형 데이터 폴백은 어떤 조건이 충족되면 제거하는 것이 안전한가요?
- 데이터 무결성 검사를 CI에 넣는다면 최소 검사 항목은 무엇인가요?

### 5. 두 명이 남은 작업의 우선순위를 어떻게 정하면 좋을까요?

현재 네트워크 안정화, 정식 UI, 콘텐츠 데이터 입력, 밸런스 작업이 동시에 남아 있습니다. 개발 인원이 두 명이라 모든 영역을 병렬로 마무리하기는 어렵습니다.

현업에서는 기능 프리즈 시점과 마무리 순서를 어떤 기준으로 결정하는지 조언을 듣고 싶습니다.

추가로 여쭤볼 내용:

- 네트워크 안정화, 사용자에게 보이는 UI, 콘텐츠 입력 중 무엇을 먼저 완료하는 것이 좋을까요?
- 새로운 기능을 멈추고 버그 수정과 사용성 개선에 집중해야 한다는 신호는 무엇인가요?
- 담당 영역이 나뉜 소규모 팀에서 특정 인원에게 지식이 몰리는 문제는 어떻게 줄이나요?

### 6. Supabase 전적 기록을 클라이언트가 직접 보내도 괜찮을까요?

현재 전적은 로컬 JSONL에 저장하고 Supabase에도 업로드합니다. 클라이언트는 anon key와 Anonymous Auth를 사용하고 RLS로 접근을 제한합니다.

이 구조에서 어느 수준까지 조작 방지를 해야 하는지, 반드시 서버에서 검증해야 하는 데이터가 무엇인지 궁금합니다.

추가로 여쭤볼 내용:

- 클라이언트가 직접 기록해도 되는 데이터와 서버 검증이 필요한 데이터의 기준은 무엇인가요?
- Photon의 사용자 정보와 Supabase의 사용자·매치 ID는 어떤 방식으로 연결하는 것이 안전한가요?
- 포트폴리오용 프로토타입과 실제 서비스에서 요구되는 보안 수준은 얼마나 다른가요?

- 임시 밸런스 수치를 코드 상수에서 데이터 테이블로 옮기는 적절한 시점은 언제인가요?
- 서드파티 에셋과 셰이더의 Unity 버전 호환 위험은 어떻게 관리하나요?
- 이 프로젝트를 취업 포트폴리오로 설명할 때 구현 기능보다 어떤 기술적 판단과 문제 해결 과정을 강조하는 것이 좋을까요?
